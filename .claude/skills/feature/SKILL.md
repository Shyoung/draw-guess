# 기능 세션 (큰 작업 하나: 기획 → GO → 개발 → 머지)

이 세션은 **기획자이면서 조율자**다. 운영자와 직접 대화하며 설계를 정하고 설계 문서를 쓴다. 코드는 직접 쓰지 않고 서브에이전트(`builder`·`qa-reviewer`·`fixer`)를 시킨다. 운영자는 큰 작업을 **동시에 하나만** 검토하므로 한 번에 기능 하나만 맡는다. 답변은 한국어. 인자는 기능 이름(slug). 없으면 ROADMAP에서 "설계 승인" 또는 "진행" 상태인 기능을 찾아 하나를 제안하고, 없으면 무엇을 만들지 묻는다.

**권장 모델**: 세션은 Opus. 신규 게임 모드처럼 규칙·프로토콜·화면을 함께 설계하는 A단계 초반에만 Fable을 권한다(`/model`로 운영자가 정한다. 세션은 스스로 바꿀 수 없다). 시작할 때 현재 모델이 이보다 낮으면 알린다. builder는 항목 크기에 맞춰 작음 Sonnet·중간 이상 Opus, QA·fixer는 Sonnet.

## 0. 시작 점검 (여기서 멈출 수 있다)
1. `date "+%F %a %H:%M"`으로 오늘을 구한다. 모든 서브에이전트 프롬프트 첫 줄에 `오늘은 YYYY-MM-DD(요일)`을 넣는다.
2. **동시에 하나**: `git fetch origin` 뒤 `git ls-remote --heads origin "feature/*"`와 ROADMAP의 큰 기능 상태를 본다. 이 기능이 아닌 다른 큰 기능이 "진행" 중이면 멈추고 보고한다.
3. **어느 단계인지 정한다**: `docs/product/`에 이 기능의 설계 문서가 있고 ROADMAP 상태가 "설계 승인" 또는 "진행"이면 **B단계**부터(문서를 읽고 진행 상황을 한 문단으로 요약한 뒤 이어 간다). 문서가 없거나 "설계 필요"·"설계 승인 대기"면 **A단계**부터.
4. **사이클과의 관계**: 이 세션은 메인 체크아웃을 쓰지 않는다. 일상 사이클이 도는 중이어도 된다.

## A. 기획 (설계가 승인되기 전)
`.claude/agents/product-planner.md`의 정의(관리 문서·설계 문서 형식·하지 않는 것)를 그대로 따른다. `.claude/skills/product-session/SKILL.md`의 대화 방식(성장 단위는 한 방, 선택지는 셋 이하와 권장안, 출처 있는 조사, 없는 기능을 있다고 하지 않기)도 같다.
1. 기획 문서 작업은 **문서용 워크트리**(CLAUDE.md "동시 작업 규칙", 폴더 `E:/claude pj/개인/draw-guess-work/product-<slug>`)에서 한다. 읽을 것: ROADMAP, BACKLOG, GAME-MODES, PRD-PLATFORM, 성장 계획 0-1·6-1·7장.
2. 운영자와 대화로 설계를 정하고 `docs/product/YYYY-MM-<slug>.md`에 쓴다(설계 문서 형식 1~8: 요약, 목표 지표, 규칙·화면, 프로토콜·파일 영향, 쪼갠 항목, 위험, 운영자가 정할 것, 변경 이력·진행 중 결함 표). 미결 항목은 운영자와 여기서 끝낸다.
3. **GO 지점**: 설계를 한 문단과 쪼갠 항목 목록(크기·순서)으로 요약하고 "이 범위로 만들까요?"를 묻는다. GO를 받으면 ROADMAP 상태를 "설계 승인"으로 바꾸고 BOARD "방향 메모"에 `날짜: <설계명> GO(기능 세션)` 한 줄을 남긴다. 신규 기능·모드는 GO 없이 개발하지 않는다.
4. 문서만 경로를 명시해 `git add` → 커밋 → `git fetch origin && git rebase origin/develop && git push origin HEAD:develop`. 끝나면 문서용 워크트리와 브랜치를 지운다. 이어서 B단계로 간다(같은 세션에서 계속하거나, 컨텍스트가 길면 저장 후 새 세션에서 `/feature <slug>`).

## B. 개발 (설계 승인 뒤)
### B-1. 워크트리 준비 (없을 때만)
```
git fetch origin
git worktree add "E:/claude pj/개인/draw-guess-work/feature-<slug>" -b feature/<slug> origin/develop   # 브랜치가 이미 있으면 -b 없이 기존 브랜치로
cd "E:/claude pj/개인/draw-guess-work/feature-<slug>" && npm ci
```
- `npm ci`는 세션이 직접 한다(운영자가 설치할 필요 없다). node_modules를 메인과 연결(junction)하지 않는다. 워크트리를 지울 때 원본이 지워질 수 있다.
- **테스트 포트**: 테스트 파일들의 포트가 고정이라, 일상 사이클이 테스트를 돌리는 동시에 이 세션이 테스트를 돌리면 충돌한다. BACKLOG의 "테스트 포트 오프셋" 항목이 완료되기 전에는 사이클과 시간이 겹치지 않게 테스트를 돌린다(포트 사용 중 오류가 나면 잠시 뒤 재시도). 완료된 뒤에는 `TEST_PORT_OFFSET=1000`을 붙여 돌린다.

### B-2. 항목 반복 (설계 문서 5번 "쪼갠 목록" 순서대로, 한 번 실행에 최대 3항목)
1. **모델 표를 먼저 출력한다.** 서브에이전트마다 `.claude/skills/ops-cycle/SKILL.md` 0-1의 규칙으로 고른다(builder: 작음 Sonnet·중간 이상 Opus).
2. 항목 시작 전에 `git fetch origin && git rebase origin/develop`. 충돌하면 양쪽 변경을 살려 풀고, 못 풀면 멈추고 보고한다(강제 push 금지).
3. `builder`에게 이 워크트리 경로를 알려 주고 그 항목만 구현하게 한다. 프롬프트에 넣을 것: 워크트리 경로, 설계 문서 경로, 항목 번호, "메인 체크아웃 경로에서 작업하지 말 것", "`git add`는 경로 명시, `-A` 금지", "PROTOCOL.md가 바뀌면 같이 고칠 것", 그리고 feature 예외 세 가지 — **① 브랜치가 develop이 아니어도 멈추지 않는다 ② push는 `origin feature/<slug>` ③ BACKLOG는 갱신하지 않는다(완료 표시는 설계 문서 ✅로만)**.
4. **builder가 끝나면 QA를 기다리지 않고 먼저 운영자에게 B-4 안내(접속 주소·확인할 것)를 출력한 다음, 같은 턴에 `qa-reviewer`를 백그라운드로 시작한다**(Agent는 기본이 백그라운드). 에이전트의 코드 단위 QA와 운영자의 눈 확인이 동시에 진행된다. 이 동안 규칙:
   - qa-reviewer는 코드를 고치지 않고 테스트용 서버를 테스트 포트(3130·3140·3456)에서만 띄우므로, 운영자의 미리보기 서버(3200)와 충돌하지 않는다.
   - **QA가 도는 동안 들어온 운영자 피드백은 바로 코드에 반영하지 않는다**(검증 중인 코드 위에 덮지 않는다). B-3대로 설계 문서와 변경 이력에는 즉시 적고 "접수, QA·fixer 끝난 뒤 반영"이라고 답한 뒤, QA(와 fixer)가 끝나면 한 번에 builder에게 시킨다.
   - QA가 결함을 찾아 fixer가 코드를 바꾸면 "코드가 바뀌었으니 서버를 다시 켜서 새로고침해 달라"고 알린다.
   - 운영자가 눈으로 먼저 문제를 찾았어도 QA 결과는 끝까지 받는다. 둘 다 끝나야 항목이 닫힌다.
   - qa-reviewer에게는 **로컬 검증만** 시킨다(스테이징 확인은 생략. feature 브랜치는 스테이징에 배포되지 않는다). **TEST-LOG는 쓰지 않는다.** 결함은 설계 문서의 "진행 중 결함" 표(ID·심각도·재현·상태)에 기록하게 하고, 열림 결함이 있으면 `fixer`를 부른다(fixer도 그 표에서 닫는다). 이 표는 설계 문서의 예외로 이 세션 몫이다.
5. 항목이 끝나면 설계 문서의 해당 항목에 완료 표시(`✅ 날짜 커밋해시`)를 하고 커밋한 뒤 `git push origin feature/<slug>`(백업, 배포 안 됨).

### B-3. 운영자 직접 피드백 (로컬에서 확인한 뒤 세션에서 바로 말한 것)
이 세션이 기획자이므로 **설계를 직접 고친다.** 운영자의 직접 지시가 곧 승인이라 별도 GO는 필요 없다. 설계 문서가 먼저, 코드가 나중이다.
- **같은 기능 안의 변경**(규칙 세부·화면 배치·문구·수치·흐름 조정, 쪼갠 항목 재조정 포함): ① 설계 문서를 고치고 ② 문서 끝 "변경 이력" 표에 한 줄(날짜·바꾼 내용·이유) ③ 쪼갠 목록에 영향이 있으면 항목을 고치거나 추가 ④ `builder`에게 시켜 반영(B-2와 같은 프롬프트 규칙, 반영 뒤 qa-reviewer 로컬 검증). 이미 만든 부분을 뒤엎어야 하면 반영하기 전에 "이미 끝난 항목 N이 다시 작업된다"를 한 줄로 알리고 확인받는다.
- **별개 기능이 되는 변경**(다른 모드·다른 기능을 새로 얹는 수준): 이 기능에 넣지 않는다. 운영자 요청을 변경 이력에 `분리(후속 기능)`으로 적고, 머지 뒤 기획 세션이나 다음 `/feature`에서 다루도록 안내한다. 판단이 애매하면 한 줄로 묻는다.
- 그 밖의 원칙(동시에 하나, 승인 없는 신규 기능 금지)은 그대로다.

### B-4. 항목 끝날 때마다 로컬 확인 방법 안내
**builder 완료 직후, QA 시작과 동시에** 안내한다(QA 결과를 기다리지 않는다). 항목(또는 피드백 반영)이 끝날 때마다 운영자가 바로 따라 할 수 있게 아래를 알려 준다. 워크트리 경로는 실제 값으로 채운다. 포트는 테스트 포트(3130·3140·3456)와 겹치지 않는 3200을 기본으로 하고, 사용 중이면 다른 번호를 쓴다.
```
cd "E:/claude pj/개인/draw-guess-work/feature-<slug>"
# PowerShell
$env:ALLOW_SOLO='1'; $env:PORT='3200'; npm start
# Git Bash: ALLOW_SOLO=1 PORT=3200 npm start
```
- 접속 주소: 먼저 `node scripts/local-urls.js 3200`을 실행해(워크트리 폴더에서) 나온 값을 **그대로 적는다** — `http://localhost:3200`(이 PC)과 `http://<LAN IP>:3200`(같은 Wi-Fi의 폰·다른 기기). 혼자서도 게임 시작 가능, 여러 명 확인은 탭·시크릿 창을 여러 개 연다. 폰이 다른 망이거나 LAN 주소가 안 열리면 아래 터널을 쓴다.
- 폰용 터널(같은 PC에서 서버를 켠 채로 다른 터미널에서): `cloudflared tunnel --url http://localhost:3200` (없으면 `npx localtunnel --port 3200`). 출력된 https 주소를 폰에서 연다. 터널 주소는 세션이 끝나면 버리고, 공개된 동안 링크를 남에게 보내지 않는다.
- 이번 항목에서 확인할 것을 2~3줄로 덧붙인다(설계 문서 쪼갠 목록의 "끝났을 때 확인할 것").
- 서버 실행은 운영자 몫이다. 세션이 서버를 계속 띄워 두지 않는다.

### B-5. 세션 끝 (항목을 다 했거나 3항목이 끝났을 때)
- 진행률 갱신: ROADMAP의 해당 항목 상태를 `진행 (feature/<slug>, n/m)`으로 바꾸는 **한 줄 변경만** develop에 반영한다. 이 세션의 워크트리는 feature 브랜치이므로 문서용 임시 워크트리(CLAUDE.md "동시 작업 규칙")를 따로 만들어 rebase 후 push하고 지운다.
- **기능이 완성되면**(모든 항목 ✅, **진행 중 결함 표의 열린 결함 0건**): 전체 테스트(`npm test`·`npm run test:browser`·`npm run test:mobile`) 통과 → `git fetch && git rebase origin/develop` → 다시 전체 테스트 → `git push origin HEAD:develop`(스테이징 배포). 이어서 ROADMAP 상태를 "스테이징(QA 대기)"로 바꾸는 문서 변경을 push하고, feature 브랜치·워크트리를 지운다(`git worktree remove` 후 `git push origin --delete feature/<slug>`). main 머지는 하지 않는다. 다음 `/ops-cycle`이 스테이징 QA를 하고 머지 GO를 묻는다.
- **머지 뒤 상위 문서 점검**: 변경 이력 때문에 `docs/GAME-MODES.md`·`docs/PRD-PLATFORM.md` 같은 상위 문서가 최종 설계와 어긋날 수 있으면(이 세션은 그 문서를 고치지 않는다) ROADMAP 상태 줄을 `스테이징(QA 대기) · 문서 정리 필요`로 표시한다. 기획 세션이 상위 문서를 정리한 뒤 이 표시를 지운다.
- 마지막 메시지: ① 이번에 끝낸 항목과 커밋 ② 남은 항목 수 ③ 운영자가 로컬·폰으로 확인할 것(B-4 안내) ④ 이번 세션에 반영한 운영자 피드백(변경 이력) ⑤ 막힌 것·운영자 결정이 필요한 것.

## 하지 않는 것
- main 체크아웃·머지·push. GO 없는 신규 기능 개발. 설계에 없는 범위 추가(운영자의 직접 지시로 설계에 먼저 반영한 것은 예외). 별개 기능의 직접 처리. 신규 기능 두 개 동시 진행. 개인정보 처리방침 변경. `docs/marketing/` 수정. 비밀 값 커밋.
- 설계 문서의 "운영자가 정할 것"이 미결이면 해당 항목 앞에서 멈추고 운영자와 결정한다.
