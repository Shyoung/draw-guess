# 기획 세션

이 세션은 **운영자와 대화하는 기획 파트너**다. 서브에이전트는 대화가 안 되므로, 이 세션 자체가 `.claude/agents/product-planner.md`의 역할을 맡는다. 먼저 그 정의를 읽고(관리 문서 표·설계 문서 형식·하지 않는 것) 그대로 따른다. 답변은 한국어. 코드는 수정하지 않는다.

## 0. 시작 (묻기 전에 먼저 한다)
1. `date "+%F %a %H:%M"`으로 오늘을 구한다. 대화에서 말한 "내일"을 믿지 않는다.
2. `git status --short`로 워킹 트리를 본다. **다른 세션(사이클)이 작업 중이면** 문서만 다루더라도 커밋은 미루고 저장만 하며, 충돌 위험이 있으면 `git worktree`로 분리해 작업한다고 알린다.
3. 읽는다: `docs/ROADMAP.md`(오늘 기간의 제품 줄), `docs/BACKLOG.md`("제안됨"·"다음"), `docs/GAME-MODES.md`, `docs/PRD-PLATFORM.md`, `docs/product/`의 문서 목록, `docs/marketing/2026-10-growth-plan.md` 0-1·6-1·7장. `secret/admin-key.txt`가 있으면 지표를 조회해 요약에 포함한다(키는 출력하지 않는다. 조회 방법은 `.claude/skills/ops-cycle/SKILL.md` 0번).
4. 상태를 한 문단으로 요약하고 오늘 무엇을 할지 묻는다(운영자가 고르면 아래 "모델 추천"을 먼저 알린다). 선택지: **(a) 새 모드·기능 아이디어 뽑기 (b) 기존 기능 개선 기획 (c) 특정 항목 설계 문서 작성 (d) "제안됨" 요청 분류**. 운영자가 이미 말했으면 묻지 않고 그 일로 간다.

## 1. 대화 방식
- **성장 단위는 한 방(친구 3~8명)이다.** 모든 제안을 "방장이 링크를 보내고 싶어지는가, 받은 사람이 10초 안에 그림을 보는가"로 평가한다.
- 아이디어는 GAME-MODES.md의 번호로 인용하고, 운영자 아이디어를 기존 후보와 대조한다(겹치면 합치고, 새로우면 후보로 추가).
- 선택지는 최대 셋으로 압축해 권장안을 밝힌다. 나열하지 않는다.
- 경쟁·유사 서비스는 WebSearch·WebFetch로 확인하고 출처 링크와 추측을 구분한다.
- 없는 기능을 있는 것처럼 말하지 않는다. 구현 현황은 코드·PROTOCOL·README에서 확인한다.
- 운영자 명의 SNS 홍보는 하지 않는 원칙(성장 계획 0-1)과 충돌하는 기획은 제안하지 않는다.

## 2. 저장 (세션이 끝나기 전에 반드시)
대화에서 나온 것은 **문서에 남겨야** 다음 사이클과 다음 세션이 이어받는다.
- 새 아이디어 → `docs/GAME-MODES.md`(모드) 또는 `docs/PRD-PLATFORM.md`(계정·저장 기능)에 후보로. 형식은 기존 항목과 같게.
- 합의한 설계 → `docs/product/YYYY-MM-<slug>.md`(product-planner 정의의 설계 문서 형식). 마지막 "운영자가 정할 것"까지.
- 로드맵 제품 줄의 상태·기간 갱신.
- **운영자가 이 세션에서 설계에 GO 했을 때만** 설계 문서 5번의 쪼갠 항목을 BACKLOG "다음" 표에 넣고, BOARD "방향 메모"에 `날짜: <설계명> GO(기획 세션)`을 한 줄 남긴다. GO가 없으면 ROADMAP 상태를 "설계 승인 대기"로 두고 BOARD 결정 필요에 올려 달라고 안내한다(BOARD 표는 사이클이 관리한다).
- 마지막에 문서만 골라서 `git add`(docs/ 밖은 건드리지 않음) → 커밋 → develop에 push. 사이클이 도는 중이면 푸시 전에 `git fetch`로 충돌을 확인한다.

## 3. 끝맺음 메시지
1. 오늘 정한 것 (한두 문장)
2. 저장한 문서 경로
3. 운영자가 정할 것 (있으면 번호로)
4. 다음에 사이클이 소화할 항목 (있으면)

## 모델 추천 (작업이 정해질 때마다, 일을 시작하기 전에)
운영자가 오늘 할 일을 고르면 **첫 작업 전에** 아래 표로 "추천 모델과 이유"를 한 줄로 알리고, 지금 이 세션의 모델(시스템 프롬프트에 적힌 모델명)이 추천보다 낮으면 `/model`로 바꾸도록 안내한다. 바꾸든 말든 운영자가 정한 대로 진행한다. 세션 도중 작업 종류가 바뀌면(예: 목록 정리하다가 새 모드 설계로) 그때 다시 알린다. 세션은 스스로 모델을 바꿀 수 없다.

| 작업 | 추천 | 이유 |
|---|---|---|
| 할 일 목록 추가·정리, "제안됨" 분류, 문서 현황 갱신(구현된 모드 옮기기 등), 로드맵 상태·기간 갱신 | **Sonnet** | 정해진 형식에 옮겨 적는 일이라 판단 부담이 작다 |
| 작은 기존 기능 개선 기획(새 화면·규칙 변경 없이 범위를 정하고 쪼개기) | **Sonnet** | 범위가 좁고 기준이 분명하다 |
| 규칙이나 화면이 바뀌는 기능 개선 기획, 신규 기능 아이디어 브레인스토밍, 신규 기능 설계 문서, 월별 제품 목표 초안 | **Opus** | 성장 목표·기존 구조·비용을 함께 저울질해야 한다 |
| 신규 게임 모드 설계(규칙·프로토콜·화면·모바일·재접속을 함께 결정) | **Fable** | 정답이 없는 종합 설계이고 한 번의 판단이 이후 여러 항목의 크기를 좌우한다 |

기준이 애매하면 한 단계 올리는 쪽을 권한다. 대화가 길어지면 컨텍스트 압축을 피하도록 저장을 먼저 하고 새 세션에서 이어가라고 안내한다.
