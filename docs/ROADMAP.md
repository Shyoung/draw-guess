# 이뭔그 로드맵 (2026 Q4)

작성 2026-09-30 · 갱신은 월 초와 회고 뒤 · 상태: **뼈대**(월별 목표 숫자는 2026-10-12 2주 회고 뒤 확정)

## 규칙
- **북극성 지표는 팀 공통 하나**: 완료된 게임 수. 마케팅·제품·개발 목표는 모두 여기에 어떻게 기여하는지로 쓴다. 지표 출처는 `/admin/stats`([성장 계획 7장](marketing/2026-10-growth-plan.md)).
- **날짜는 항상 절대 날짜로 적는다.** "내일", "다음 주"를 쓰지 않는다. 항목마다 시작일~종료일과 상태(예정 / 진행 / 설계 필요 / 설계 승인 대기 / 완료 / 보류)를 붙인다. 세션은 시계(`date`)로 오늘을 구해 해당 기간 줄만 본다.
- **월별 목표는 팀당 3~4줄.** 숫자는 기준값이 있을 때만 쓰고, 없으면 `[측정 뒤 확정]`.
- **큰 작업(신규 모드·큰 기능)은 동시에 하나만.** 상태는 `설계 필요 → 설계 승인 대기 → 설계 승인 → 진행 (feature/<이름>, n/m) → 스테이징(QA 대기) → 완료`로 표기한다. 개발은 `/feature`이 feature 브랜치에서 소화하고, 일상 사이클은 작은 BACKLOG 항목을 병행한다.
- **운영자 GO는 세 곳**: ① 월별 목표 ② 신규 기능·모드 설계 문서 ③ 프로덕션 머지.

## 흐름
```
마케팅 개선 요청 ──▶ BACKLOG "제안됨" ──▶ 제품 분류 ─┬─ 작은 개선 ──▶ BACKLOG "다음" ──▶ ops 사이클
                                                 ├─ 신규 기능·모드 ▶ 로드맵 + 설계 문서 ─▶ 운영자 GO ─▶ 쪼갠 항목 ▶ BACKLOG "다음" ─▶ ops 사이클
                                                 └─ 하지 않기(이유 기록)
```
개발 레인은 둘이다. **작은 항목**(BACKLOG)은 일상 사이클의 builder가 develop에서 하나씩 소화하고, **큰 기능**은 설계 승인 뒤 기능 세션이 feature 브랜치에서 설계 문서의 쪼갠 항목을 순서대로 소화한 뒤 완성 시 develop에 머지한다. 큰 기능은 동시에 하나만 진행한다. 큰 작업의 builder에는 Opus·Fable을 쓴다.
